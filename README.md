# gpu-vanity-ssh-key

A GPU-accelerated vanity ed25519 SSH key generator for Apple Silicon Macs.
It grinds random keypairs on the GPU via Metal until your public key's
base64 ends with a string of your choosing (e.g. `/alice12`), then writes
you a normal `id_ed25519` / `id_ed25519.pub` pair.

**Requires an Apple Silicon Mac (M1 or later).** It won't build or run on
Intel Macs, Linux, or Windows -- this is Metal Shading Language, not
portable code. If you want a vanity key tool that runs anywhere, there are
CPU-based options on GitHub for that; this one specifically exists to see
how fast the search can go on a GPU.

## Why this exists, and why it's not just "fast"

A vanity SSH key is normally generated by brute force on the CPU: generate
a random keypair, check if the public key ends the way you want, repeat.
Doing that on a GPU means writing the actual elliptic-curve math -- modular
arithmetic over a 255-bit prime, Edwards-curve point operations, and
SHA-512 -- directly in a shader language, where a single wrong constant or
a subtle bug silently produces wrong keys instead of crashing.

So this project is built test-first: every layer (field arithmetic, point
arithmetic, SHA-512, the full seed-to-pubkey derivation) is checked with
property-based tests against independent, trusted references -- including
an end-to-end check against Python's `cryptography` library across
thousands of random seeds -- before being trusted. See [`tests/README.md`](tests/README.md)
for the full story, including one real bug (a memory leak) and one real
finding (the GPU kernel turned out to be occupancy-bound, not
arithmetic-bound, so an optimization that should have tripled throughput
only bought about 10%).

As a second line of defense, the program never writes a key straight from
GPU output: any candidate match is independently re-derived using Apple's
own CryptoKit (not this project's Metal code) before anything touches
disk. If CryptoKit ever disagrees, the program refuses to write and prints
a warning instead -- that would mean a bug in the GPU implementation, not
something to quietly paper over.

## Build

```
swiftc -O grind.swift -o grind -framework Metal -framework Foundation -framework Security -framework CryptoKit
```

That's it -- no package manager, no dependencies beyond Xcode's command
line tools (`xcode-select --install` if you don't have `swiftc` yet).

## Run

```
./grind --suffixes=/alice12,+Alice12
```

- `--suffixes` (required): comma-separated list of targets. **Each one
  must be exactly 7 characters**, using only base64 characters
  (`A-Z a-z 0-9 + /`) -- that's what the kernel is compiled to compare
  against the last 7 characters of your public key's base64. You can list
  several (e.g. both a `/` and `+` variant, or different capitalizations)
  to search for any of them at once.
- `--batch-size` (default 2,000,000): how many keys to generate per GPU
  dispatch. 1-2 million is a reasonable default on an M-series chip.
- `--out` (default `.`): directory to write `id_ed25519` / `id_ed25519.pub`
  into.
- `--comment` (default `vanity-key`): comment embedded in the key.

It prints progress every 30 seconds (tries, rate, ETA) and keeps running
until it finds a match.

### How long will it take?

Expected number of tries is `(64^length) / (number of targets)`. For a
single 7-character target, that's 64^7 ≈ 4.4 trillion tries on average.
Measured throughput on an M-series Mac mini is roughly **650,000-700,000
keys/sec**, which works out to **days, not minutes** for a specific
7-character ending. Listing a few equivalent targets (different
capitalization, `/` vs `+`) cuts that down proportionally -- 4 targets
means a quarter of the expected wait.

If you want something fast enough to find in minutes, go shorter -- see
"Changing the target length" below.

### Running it in the background for days

`grind` doesn't daemonize itself. If you want it to survive you closing
your laptop lid or logging out, the simplest approach on macOS is a
LaunchAgent:

```xml
<!-- ~/Library/LaunchAgents/com.example.vanity-grind.plist -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.example.vanity-grind</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/bin/caffeinate</string>
        <string>-s</string>
        <string>/path/to/grind</string>
        <string>--suffixes=/alice12,+Alice12</string>
        <string>--out=/path/to/output/dir</string>
    </array>
    <key>WorkingDirectory</key>
    <string>/path/to/this/repo</string>
    <key>StandardOutPath</key>
    <string>/path/to/output/dir/grind.log</string>
    <key>StandardErrorPath</key>
    <string>/path/to/output/dir/grind.err</string>
    <key>RunAtLoad</key>
    <true/>
    <key>KeepAlive</key>
    <dict>
        <key>SuccessfulExit</key>
        <false/>
    </dict>
</dict>
</plist>
```

Replace every `/path/to/...` and the label, then:
`launchctl load ~/Library/LaunchAgents/com.example.vanity-grind.plist`

`caffeinate -s` keeps your Mac awake for as long as `grind` is running.
`KeepAlive`/`SuccessfulExit: false` restarts it if it crashes, but leaves
it stopped once it finds a match and exits successfully. A LaunchAgent
only runs while you're logged in (unlike a system LaunchDaemon, which
needs `sudo` to install); that's the simpler option for a laptop you
actually use day to day.

Check progress any time with `tail -f /path/to/output/dir/grind.log`.

### Changing the target length

The kernel is compiled with a fixed `TARGET_LEN` (7) in `fe25519.metal`,
for simplicity -- all targets must share one length. To search for
something shorter (faster) or longer (slower) than 7 characters, edit
`#define TARGET_LEN 7` near the `k_grind` kernel and rebuild. Going from 7
to 5 characters cuts the expected search time by roughly 4096x (64²); going
to 8 multiplies it by 64.

## How it works, briefly

1. **Field arithmetic** (`fe25519.metal`): arithmetic over GF(2^255 - 19),
   ported from libsodium's portable `fe_25_5` representation.
2. **Point arithmetic**: Edwards-curve operations in extended coordinates,
   also ported from libsodium's ref10 implementation, plus a precomputed
   table of `2^i * B` for `i = 0..255` (`base_table.bin`, regeneratable
   with `generate_table.py`) so the scalar-multiplication loop does one
   point addition per set bit of the scalar instead of an unconditional
   doubling every bit.
3. **SHA-512**: standard FIPS 180-4, specialized for exactly one 32-byte
   input block.
4. **Grind kernel** (`k_grind`): seed → SHA-512 → clamp → scalar·B →
   compress → base64 → compare the last 7 characters against your targets,
   all per-GPU-thread, batched across millions of threads per dispatch.
5. **Host harness** (`grind.swift`): generates random seeds, dispatches
   batches, and on a match independently re-derives and verifies the
   keypair with CryptoKit before writing anything to disk.
